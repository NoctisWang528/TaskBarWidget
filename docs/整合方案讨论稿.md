# TaskBarWidget 整合方案讨论稿

更新日期：2026 年 10 月 13 日。状态：需求已确认，2026 年 10 月 13 日获准开始本地实现与构建；桌面体验由用户验收。

已建立独立的 [TaskBarWidgets 产品目录](../TaskBarWidgets/README.md)，当前实现与自动验证结果见[验收记录](../TaskBarWidgets/ACCEPTANCE.md)。下文保留目标设计与验收要求；目标条目不等于全部已验收。根据本轮实际反馈，任务栏、硬件与媒体已迁入同一个现代设置窗口，左键面板采用横向双卡片；最新规划见[统一界面方案](../TaskBarWidgets/docs/界面统一方案.md)。候选构建与迁移配置位于 `TaskBarWidgets/artifacts/app-next/`，遵照用户要求未启动。

建议以 TrafficMonitor 为基底，保留任务栏宿主、硬件监测、插件和现有布局能力，复用 TaskbarLyrics 的歌词与媒体能力，借鉴 AF-Media-Bar 的音频控制及现代界面。最终只提供一个启动入口，由一个任务栏宿主统一管理显示区域。

首版以完整日用体验为交付目标。开发过程可以分阶段验证，但逐字歌词、动画、音频输入输出控制和统一交互都属于完整交付范围，不能用仅能运行的原型代替成品。本文区分用户已确认需求与建议方案；技术路线仍需通过原型验证。

## 选择 TrafficMonitor 的依据

| 基底 | 可直接保留 | 主要代价 | 判断 |
| --- | --- | --- | --- |
| TrafficMonitor | 任务栏、监测、布局、现有插件及个人配置 | 需要接入 C# 歌词逻辑并更新界面 | 推荐，最符合最高优先级 |
| TaskbarLyrics | 歌词、媒体识别、WebView2 效果 | 需要移植 TrafficMonitor 监测与布局，并处理原生插件兼容 | 会重做用户最想保留的部分 |
| AF-Media-Bar | 现代 WPF 界面、媒体及音频服务 | 仍须迁移完整监测、布局和插件体系 | 更适合作为功能与视觉参考 |

TrafficMonitor 的布局已有显示项排序、单双行组织、标签与数值、独占双行项、间距、字体颜色和插件绘制。这里的“保留可自定义布局”是保留这些真实能力；不把它擅自扩张为自由拖拽画布，也不缩减成少数固定模板。依据：[任务栏布局实现](../TrafficMonitor/TrafficMonitor/TaskBarDlg.cpp)、[设置模型](../TrafficMonitor/TrafficMonitor/CommonData.h)。

## 建议的技术结构

### 一个任务栏宿主和一个内部辅助程序

建议保留 TrafficMonitor 的 C++ 主程序，并增加一个由它管理的 C# 辅助程序。用户只启动和退出一个产品，内部职责如下。

| 部分 | 职责 | 复用方式 |
| --- | --- | --- |
| TrafficMonitor 主程序 | 监测、插件、任务栏位置与尺寸、Explorer 恢复、显示模式决策 | 延续现有 C++ 实现 |
| 原生监测视图 | 按原布局显示监测指标和插件 | 保留现有绘制及布局计算 |
| 媒体视图 | 歌词、封面、动画、频谱、浏览器媒体控件 | 在 TrafficMonitor 内托管 WebView2，复用歌词 Web 资源 |
| C# 辅助程序 | 媒体会话、歌词获取与同步、缓存、音频设备和音量 | 复用 TaskbarLyrics Core 及所需 App 服务；移植 AF 音频服务并补齐输入端 |
| 控制面板与设置页 | 统一交互、外观与配置编辑 | 使用 C# 窗口宿主，复用现有控件和网页资源，统一导航与样式 |

辅助程序不启动原 TaskbarLyrics 或 AF-Media-Bar 的任务栏窗口、托盘、自启与更新器。它不是第三个独立产品，也不能自行占用另一段任务栏。

此方案有两个自有进程，WebView2 还会产生浏览器、渲染等运行时进程。因此“一个产品”不等于“任务管理器里只有一个进程”。资源占用必须统计整个产品的进程树。

新应用所有代码、复制的依赖、资源、测试和构建脚本均归入 `TaskBarWidgets/`。原 `TrafficMonitor/`、`TaskbarLyrics/`、`AF-Media-Bar/` 为只读参考；允许复制必要实现，禁止在新产品中以项目引用、链接资源、构建前复制等方式依赖原目录。移开三个参考目录后，新产品仍须能独立还原、编译和打包。来源许可证和说明随复制内容保留。

### 保留歌词效果的方式

优先复用 [歌词 Web 资源](../TaskbarLyrics/TaskbarLyrics.App/Web/Lyrics/index.html)、[动画场景实现](../TaskbarLyrics/TaskbarLyrics.App/Web/Lyrics/presentation.js)和[显示消息构造](../TaskbarLyrics/TaskbarLyrics.App/LyricsWebViewScriptFactory.cs)，不要在 C++ 中另写一套近似歌词动画。

WebView2 控件由 TrafficMonitor 的任务栏宿主创建，媒体和监测视图共用同一受管理区域，互斥显示。C# 辅助程序传递媒体和歌词数据，控制面板则作为普通弹出窗口定位到任务栏区域上方。

原型必须验证 WebView2 与现有透明窗口、DirectComposition、DPI、命中测试及插件绘制能否协调工作。优先评估能够满足要求的简单托管方式；需要精确合成和统一输入时使用 CompositionController。微软说明 Visual hosting 需要宿主承担输入转发及缩放处理，这不是复制 HTML 就能完成的接入。[WebView2 托管方式](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/windowed-vs-visual-hosting)

不采用把辅助程序的 WPF 窗口跨进程强行挂到 TrafficMonitor 窗口下面的默认方案。跨进程 `SetParent` 存在 DPI 重置等约束；保留既有 Explorer 接入边界，避免再增加一层此类关系。[SetParent 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent)

若嵌入验证失败，需重新比较媒体视图承载方式，不能静默降低歌词效果，也不能回到多个应用各自抢占任务栏的状态。

### 通信与配置归属

建议使用当前用户范围的本地命名管道传递结构化数据与命令，不开放本地 HTTP 服务。协议包含版本、会话标识、曲目标识、序号及命令结果，丢弃切歌或重连后的旧响应；UI 线程不等待网络或管道返回。

主程序负责模式及布局配置；辅助程序负责歌词、播放器、音频偏好与歌词缓存。每类数据只有一个写入者，设置页面发送命令并等待应用结果，避免两个进程同时改写同一 INI 文件。已有监测字段与插件标识保持兼容，新设置单独存储并带版本。

通信断开、辅助程序崩溃或 WebView2 故障时，任务栏恢复监测视图，并提供简短失败提示及重试入口。恢复成功后依据最新媒体状态重新显示，退出时完整清理辅助程序及窗口资源。

单进程 C++ 全移植会重写成熟的歌词匹配、缓存和界面代码；进程内加载现代 .NET 又增加运行时互操作复杂度。现有硬件包装项目使用 C++/CLI 与 .NET Framework 4.7.2，它不是可以直接装入现代 .NET 歌词程序集的现成桥梁。内部辅助程序是当前建议，尚未通过实测证明最优。

## 显示模式与切换规则

将“选中的媒体会话”和“任务栏显示模式”分开。看系统信息时仍能通过面板控制当前媒体；隐藏歌词不停止硬件采样，也不丢失正在播放的曲目进度。

### 自动模式

| 条件 | 任务栏内容 | 行为 |
| --- | --- | --- |
| QQ 或网易云正在播放，歌词可用 | 完整歌词视图 | 整块切换，可按设置显示封面、翻译、逐字高亮 |
| QQ 或网易云正在播放，正在取词 | 曲名与取词状态 | 不显示上一首歌词，不因网络等待来回切模式 |
| QQ 或网易云正在播放，无歌词或纯音乐 | 根据设置显示频谱或曲目信息 | 保留 TaskbarLyrics 的频谱策略；建议默认启用无歌词频谱 |
| 没有音乐播放器播放，浏览器媒体正在播放 | 标题、来源及播放控件 | 不检索或显示歌词；是否可控取决于该媒体会话的能力 |
| 所有有效媒体均暂停、停止或消失 | 系统监测视图 | 恢复原布局，短暂的切歌空窗不造成闪烁 |
| 媒体模块不可用 | 系统监测视图 | 硬件监测继续工作 |

建议 QQ／网易云的正在播放会话优先于浏览器；两者同时播放时保留当前有效选择，支持面板手动选择来源与设置优先级。这里的具体多源仲裁策略尚属建议，不直接跟随 Windows 当前会话的每次变化。

系统媒体接口只能读取已接入 SMTC 的会话，因此不能承诺任意网页视频都有标题、时间轴和播放控制。无会话的普通系统声音不自动抢占监测视图。[微软媒体会话接口](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionmanager)

### 滚轮与手动选择

建议上滚进入当前媒体视图，下滚进入系统信息，方向固定且可配置。高精度滚轮累积阈值后切换一次，避免一个手势连续来回切换。

用户已确认：手动选择保留到下一次有效播放状态变化，再恢复自动。曲目变化、进度更新、音量变化和封面变化不重置手动选择。建议仅当前选中会话的播放／暂停／停止，以及因会话关闭导致的有效源切换触发重置，后台无关会话不得打断用户查看。

暂停时手动进入媒体视图，建议显示冻结的当前歌词或最近曲目信息与恢复播放按钮；没有可用会话则保持系统信息。右键菜单提供“自动切换”入口，可立即解除手动选择。

## 鼠标交互与控制面板

| 操作位置 | 操作 | 建议行为 |
| --- | --- | --- |
| 任务栏正文或空白 | 左键单击 | 展开或收起统一控制面板 |
| 浏览器模式的播放按钮 | 左键单击 | 执行对应命令，不同时打开面板 |
| 任务栏区域 | 右键 | 打开设置菜单，屏蔽 WebView 默认浏览器菜单 |
| 任务栏区域 | 滚轮 | 切换媒体与系统信息，不兼任音量调节 |
| 控制面板音量滑块 | 拖动或滚轮 | 调整对应设备音量，不切换任务栏模式 |
| 面板外部或 Esc | 单击或按键 | 收起面板 |

统一左键与插件的既有点击处理存在冲突：当前 TrafficMonitor 会先把左键交给插件。建议产品默认左键统一开面板；插件专属功能从右键子菜单进入，必要时提供修饰键访问。具体保留哪些插件交互需要结合日用习惯确认。双击默认不增加动作，原有映射可作为高级设置，避免一次双击触发两种操作。

控制面板建议分为三个区块，音频部分在没有媒体时仍然可用：

```text
┌──────────────────────────────┐
│ 封面  曲名 / 歌手       播放源 │
│       上一首  播放/暂停 下一首 │
│       播放进度与时间           │
├──────────────────────────────┤
│ 输出设备                 选择 │
│ 扬声器音量              静音 │
├──────────────────────────────┤
│ 输入设备                 选择 │
│ 麦克风音量              静音 │
└──────────────────────────────┘
```

进度拖动、上一首和下一首按会话能力启用。不能执行时给出明确状态，不能显示一个实际无效的按钮。右键菜单保持简短：设置、自动切换、显示模式、歌词校准、插件与诊断、退出。

## 输入输出设备控制

[AF 音频设备服务](../AF-Media-Bar/src/AFMediaBar/Classes/Services/Audio/AudioDeviceService.cs)当前枚举输出端点；[默认端点切换](../AF-Media-Bar/src/AFMediaBar/Classes/Interop/AudioPolicyConfig.cs)写入 Console 和 Multimedia 角色，没有切换 Communications 角色。输入设备切换与输入音量属于新增实现范围。

完整交付应包含：

- 分别列出可用输出设备和输入设备，显示当前默认项；支持设备插拔、蓝牙断连及默认项被系统更改后的刷新。
- 切换输出或输入设备后读回系统状态，成功后更新选中项；失败或部分角色切换成功时如实显示结果，不仅更新 UI。
- 输出音量、输入音量和静音分别绑定当前对应端点，与 Windows 音量变化双向同步。端点音量控制及变化通知可使用 Core Audio。[微软端点音量文档](https://learn.microsoft.com/en-us/windows/win32/coreaudio/endpoint-volume-controls)
- 默认设备与默认通信设备分别处理。建议默认保留通信角色，提供“同时设为默认通信设备”选项；用户是否希望始终联动仍待确认。
- 已指定固定设备或使用独占模式的应用，未必跟随默认设备切换；面板应表达“默认设备已切换”，不保证所有正在播放的音流即时迁移。

首版不增加尚未要求的应用级输出路由、混音器和空间音效。它们不影响本次明确要求的输入输出控制完整度。

## 歌词功能对齐清单

“达到当前 TaskbarLyrics 的效果”以本仓库版本为基线，实施前将以下清单与运行画面及现有测试逐项核对。旧技术文档部分类型名与现有实现不一致，匹配规则和默认值以源码及测试为准，不按旧文档重新实现算法。

| 功能 | 完整交付要求 |
| --- | --- |
| 获取与匹配 | 在线多来源、本地歌词、匹配修正、缓存、快速切歌取消与旧结果隔离 |
| 时间同步 | 真实播放状态、进度外推、暂停与 seek 校正、播放器和单曲偏移 |
| 歌词显示 | 当前句和下一句、逐字扫描、译文、长句处理及文字对齐 |
| 动画 | 切句、切歌、封面过渡、搜索到歌词、歌词与频谱场景切换 |
| 外观 | 字体、字号、字重、颜色、主题、背景、边框、阴影、封面与间距等已有相关设置 |
| 无歌词场景 | 纯音乐、无歌词、搜索中、来源异常及可配置频谱行为 |
| 媒体控制 | 播放／暂停、上一首／下一首、可用时拖动进度、来源选择及既有相关快捷键能力 |
| 维护能力 | 缓存清理、偏移校准、匹配修正与必要诊断，统一到新设置体系 |

逐字高亮必须依据可用歌词时间信息，不能把普通 LRC 的近似进度描述成真实逐字时间。播放器上报不足、歌词源没有译文或网络失败时保留诚实的回退状态；完整体验不等于所有歌曲都有完整数据。

频谱采集复用现有能力，隐藏频谱时停止不必要采集和刷新。若采用系统输出混音，明确它包含其他应用声音，不能称为只来自当前歌曲；输入设备控制不需要为此持续录制麦克风。

## 布局与视觉更新

监测模式保持原显示项、排序、横排／双行、标签、数值与单位、单项颜色、间距、状态图、偏移、插件和显示器选择能力。歌词模式拥有独立的文字与封面设置，两者共享窗口位置和边界，模式切换不得重写另一套布局。

建议默认沿用监测区域宽度，允许单独设置媒体宽度，并提供两种模式使用同一宽度的选项。长歌词在媒体区内部滚动或裁切；不随每句文字不断改变任务栏占用。实际宽度策略应结合用户当前布局及屏幕空间确认。

任务栏视觉以清晰、紧凑为主：统一字重、数字对齐、边距和悬停反馈，保留 MiSans 等用户字体及自定义颜色。新样式作为默认预设，不强制覆盖现有配色；不通过大面积卡片或厚背景降低信息密度。

弹出面板与设置页统一采用接近 Win11 的圆角、层级、明暗主题、焦点与键盘操作。透明材质不可用时使用清晰的实色背景。动画遵守减少动态效果偏好。

建议重绘设置页，而不是仅替换旧对话框颜色：

| 页面 | 内容 |
| --- | --- |
| 任务栏与布局 | 显示器、位置、宽度、显示项排序、单双行、间距和预览 |
| 硬件与网络 | 监测来源、传感器、采样、单位、网卡及现有通知 |
| 歌词与播放器 | 播放源、歌词源、匹配、校准、翻译、逐字与频谱 |
| 音频 | 输入输出偏好、默认角色及设备相关设置 |
| 外观与交互 | 主题、字体、颜色、背景、滚轮、点击和快捷键 |
| 常规与维护 | 自启、配置导入导出、插件、日志、诊断与关于 |

布局和外观支持实时预览及取消还原；监测参数经现有校验路径应用。所有原有任务栏设置先逐项映射再替换入口，不能因页面重绘漏掉高级配置。只有主窗口专属配置在本次裁剪范围内。

## 去掉主窗口的边界

[TrafficMonitorDlg.cpp](../TrafficMonitor/TrafficMonitor/TrafficMonitorDlg.cpp)同时承担桌面窗口和采样定时器、监测线程、任务栏创建、托盘、配置应用及 Explorer 恢复。直接删除会破坏保留功能。

建议先让它作为不可见的应用控制宿主，彻底移除显示主窗口、皮肤选择及主窗口专属设置入口，同时保证冷启动和恢复时都不闪现。待任务栏、监测和退出验收通过后，再删除已经不被依赖的绘制与资源代码。保留隐藏消息宿主不意味着保留用户不需要的桌面窗口。

无任务栏可见且托盘被隐藏时，要有恢复入口。建议任务栏接入失败时临时显示托盘，避免用户无法打开设置或退出。

## 实施顺序与交付门槛

以下是内部验证顺序，不是将完整需求分割成多个对外交付版本。

| 阶段 | 工作 | 通过条件 |
| --- | --- | --- |
| 1 基线与技术验证 | 记录当前布局、插件、传感器及资源占用；验证完整歌词 Web 接入、通信、DPI 和点击 | 一个任务栏宿主能稳定切换原监测与原歌词效果，失败不影响监测 |
| 2 功能整合 | 媒体会话、完整歌词链路、浏览器模式、滚轮状态、输入输出设备及音量 | 真实 QQ／网易云和浏览器场景通过，异步结果不会串歌或串设备 |
| 3 统一界面 | 完成控制面板、设置重绘、主题、布局预览和主窗口裁剪 | 设置能力没有遗漏，既有个人布局与插件仍可使用 |
| 4 完整验收 | 配置迁移、异常恢复、长期运行、多屏、安装目录与回退 | 可作为日常 TrafficMonitor 替代品，未解决项明确记录 |

技术验证若发现根本性冲突，应调整内部承载方案，并保持已确认体验目标，不能只把功能移到另一块悬浮区域。

### 必须覆盖的验收场景

- QQ 和网易云：播放、暂停、停止、seek、切歌、快速连切、两播放器并存；真实歌词、翻译、逐字与纯音乐效果对照。
- 浏览器：有会话／无会话、播放／暂停、与音乐同时播放、来源关闭；浏览器标题不会被发送去检索歌词。
- 滚轮：两种方向、高精度滚轮、媒体暂停时手动查看、下一次有效播放状态变化恢复自动；面板滚动不误切模式。
- 布局：原配置导入，插件项目、单双行、标签、颜色、字体和宽度不丢失；切换媒体后能原样恢复。
- 音频：扬声器／耳机／蓝牙及多个麦克风，热插拔、外部音量更改、默认通信角色、失败与部分成功反馈。
- Windows：当前构建、Explorer 重启、睡眠唤醒、任务栏自动隐藏、全屏、主副屏及混合 DPI；具体显示器与缩放组合实施前补录。
- 故障与退出：歌词网络失败、辅助程序崩溃、WebView2 失败、配置损坏、正常退出及重新启动，无残留窗口和失控重试。
- 性能：与原 TrafficMonitor 及 TaskbarLyrics 对照空闲、歌词、频谱和面板场景，统计整个进程树的 CPU、内存、句柄及长期趋势；暂不编造未经测量的资源预算。

新产品的独立构建必须包含复制到 `TaskBarWidgets/` 内的完整硬件监测工程；不得构建原目录的 `TrafficMonitor.sln`，仅通过 Lite 构建不能证明温度等硬件功能可用。复用的歌词和网页行为沿用相关测试，新模式策略、通信失效和输入端控制补充对应验证。自动检查不能替代真实 Windows 桌面验收。

## 后续讨论重点

核心功能及模式切换已确认，以下细节可在界面方案阶段集中决定：

1. 任务栏媒体宽度是否始终与监测区域相同；封面是否默认显示。
2. 现有三个插件哪些必须保留，以及哪些插件点击动作仍需快捷入口。
3. 切换麦克风和输出设备时，是否同时切换默认通信设备。
4. QQ 与网易云同时播放的默认优先级，以及多显示器的实际使用范围。
5. 上述内部辅助程序方案是否符合对资源占用与部署方式的期望；实际增量由技术验证测量。

以上细节采用本文建议作为初始默认值，实施过程中可调整，不再阻塞已授权工作。主窗口皮肤系统整体移除，不影响任务栏主题、颜色、字体和可自定义布局。


## 最新验收反馈修订（2026-10-13）

本节覆盖前文冲突决定。快捷面板按流量、设备、媒体自上而下排列，三卡等宽，热力图为正方形格子，去掉各卡关闭按钮和共同背景。多个媒体来源可点击切换。任务栏媒体和监测使用统一字体、背景及透明度，切换保留同一原生输入窗口；暂停恢复、左／右键与滚轮是桌面验收重点。设置使用 Mica 和紧凑响应式布局。
