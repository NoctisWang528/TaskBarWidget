# Internal media protocol

Transport: local named pipe `TaskBarWidgets.<native PID>`, UTF-8 JSON objects separated by LF, version 1. C# helper is a current-user-only server, native host is client. Native host launches `TaskBarWidgets.Media.exe --host-pid <PID> --pipe-name TaskBarWidgets.<PID> --portable-data <0|1>` from its adjacent `Media/` directory. The optional portable argument is the host's resolved first-run/writability decision; older four-argument launches retain INI lookup compatibility. Helper exits when parent exits. Serialize writes, cap messages at 4 MiB, observe disconnects and cancellation. No remote clients.

Helper to native:

- `{ "version":1, "type":"initialize", "renderVersion":2 }`: declares the structured native renderer contract. Sent on every connection; no HTML, CSS or scripts are transmitted.
- `{ "version":1, "type":"frame", "renderVersion":2, "revision":N, "sourceId":"...", "isPlaying":true, "hasMedia":true, "isBrowser":false, "trackId":"...", "lyrics":{...}, "style":{...}|null, "cover":{...}|null, "browser":{...}, "spectrumTuning":{...}, "spectrum":[...] }`: complete snapshot for the native DirectComposition renderer. `lyrics` carries `current`, `next`, `progress`, `currentLineIndex`, `trackId`, `isPureMusic`, `isPlaying`, `currentTranslation`, `nextTranslation`, `translationMode`, `animateTransition`, `wordScanProgress` and `scene` (`lyrics`, `searching`, `spectrum`, `message`, `noPlayback`). `style` keeps the field names and meanings produced by `NativeMediaPayloadFactory.CreateStyle`. `revision` increases only for an effective state change. The first frame of a connection is complete; later frames may send `style:null` or `cover:null` to reuse the value already applied on that connection, while an empty cover object means "clear". Changes in source/effective playback state reset native manual override; trackId alone does not. Browser frames must not query lyrics.
- `{ "version":1, "type":"error", "message":"..." }`: bounded diagnostic; not arbitrary executable content.

Native to helper:

- Left click on the taskbar opens the native card group in-process; no panel command crosses a pipe any more. The native host anchors the group at the taskbar window's horizontal centre and top edge, and the card group is dismissed by an actual outside click, Escape, a second entry click, or opening settings.
- Actions `openSettings`, `playPause`, `previous`, `next`, `shutdown` without extra fields.
- Action `seek`, `positionSeconds`: seek selected session if supported.
- Action `mediaVisible`, `visible`: whether native media renderer is visible; used to avoid hidden spectrum/render work.
- Action `openMonitorSettings`: native action originating from helper; reply may use the same command envelope helper-to-native. Native opens the unified settings window.
- Helper-to-native actions `showMedia` and `toggleMedia` support matching previews and the retained visibility hotkey; native owns the resulting manual display state.

Unified settings use helper-to-native commands `getNativeSettings` / `applyNativeSettings`, a unique string `requestId`, and `expiresAt` in Unix milliseconds. Apply carries a flat object of typed values in `payload`. The native host rejects expired or invalid requests before mutation and replies with action `nativeSettings`, the same requestId, `success`, `error`, and a schema/current-value payload: `{groups:[{id,label,page}],fields:[{key,label,group,type,value,options?,min?,max?}],configPath}`. `options` entries are `{value,label}`. Validation and persistence belong to native code. After partial failure the reply may include actual readback; the UI retains unconfirmed edits and displays the error instead of claiming success. Helper correlation expires after 12 seconds.

Built-in Battery/Power/Weather options appear as typed fields under hardware groups `builtins.battery`, `builtins.power`, `builtins.weather`. Historic DLL names only identify migrated settings; DLLs are never loaded. Unknown/credential fields are not serialized into the settings schema. Weather keys have a separate explicit write-only configuration path described below; stored keys are never returned. `pluginOperation` and the plugins page have been removed. `openSettings` can select taskbar/hardware/audio/general/about.

All normal settings entry points open the unified helper window. Native owns shared appearance (`taskbar.fontName`, font attributes, `back_color`, `transparent`, `backgroundOpacity` 0–100). Native delivers `nativeAppearance` directly to the native renderer; later helper style frames retain these shared values. The native renderer owns composition, text layout, scan animation and hit testing; wheel and right click stay native. Windows 11 does not change layered-window styles at playback transitions.

Traffic history is requested with `getTrafficHistory`, `requestId`, and `expiresAt` using the same correlation/expiry rules. Response action is `trafficHistory`; success payload is `{today:"YYYY-MM-DD",days:[{date:"YYYY-MM-DD",totalKiB:number}],scopeLabel:string}`. Days cover Monday of the current week plus the previous eleven weeks through local today. Unknown and future days are absent; explicitly recorded zero days remain present. `totalKiB` is upload plus download, with legacy total-only records counted once and the live today snapshot replacing a same-date historical record. Native owns a bounded snapshot published by the monitor writer; UI requests do not scan files or contend with file I/O. The helper requests only while the panel is visible, on open and about every ten seconds, and cancels on hide or shutdown.

Frame queues retain complete snapshots. Before serialization the helper omits an unchanged style or cover per connection; initialize/reconnect always includes the complete current style, cover and other state. A renderer reset must request a pipe reconnect so the complete state is resent. Display frames may be coalesced to the latest snapshot; commands use a separate reliable bounded queue and are never dropped.

Native owns the single taskbar area, automatic/manual display mode, wheel switching and right menu. Native pairs left-button press/release across display transitions and owns panel toggles. Browser control hit testing returns a tagged action to that same gesture; disabled controls do nothing. Renderer readiness/input/query failure falls back to the panel, and a late browser callback cannot commit a completed gesture. Left-click panel opening is handled entirely by the native card host; there is no second invocation path through Media or WinUI.

## Card lyrics and startup state (2026-10-18)

Settings simplification: global hotkey fields and `resetMediaHotkey` are removed from the settings API; legacy persisted hotkey objects are ignored. `enableControlPanel` and `syncDefaultCommunicationsDevice` are no longer configurable or serialized: the panel is always available and an explicit endpoint switch always synchronizes the communications role. Spectrum authorization/display policy remains a separate lyrics setting. `getState.sources[]` additionally contains `iconDataUrl` (bounded local application image; empty means generic icon). Icons resolve asynchronously by source ID without borrowing the active audio session's icon.

UI request `subscribeCardLyrics` has `{visible:boolean,session:integer}`. Each panel visibility generation gets its own session; a newer session supersedes an older request. An active subscription returns `{snapshot}` and receives latest-only events `{version:1,type:"command",action:"cardLyricsFrame",session,payload}`. The payload is a complete structured snapshot with `renderVersion:2`, `revision`, `trackId`, `available`, `isPlaying`, `lyrics` (current/next/progress/currentLineIndex/trackId/isPureMusic/isPlaying/currentTranslation/nextTranslation/translationMode/animateTransition/wordScanProgress/scene), `style` (the field names and meanings produced by `NativeMediaPayloadFactory.CreateStyle`), and `nativeAppearance` (the existing shared taskbar typography fields; may initially be empty). No HTML or scripts are sent. The WinUI card renders this directly with reusable native text lines. Unavailable lyrics clear the card without starting a separate search. The UI rejects stale sessions and locally resets revision ordering whenever it subscribes/reconnects, so a restarted backend with a lower revision is accepted. It stops applying frames on hide and applies the latest snapshot directly when shown again. Reconnection subscribes again. Native additionally sends `taskbarAppearance` with its shared typography payload to the media service; the card uses the same font attributes while adapting foreground contrast to its Mica theme.

Native settings readback includes `startup:{enabled,status,registeredPath,currentPath,needsRepair,error,legacyPath}`. `enabled` means a verified current-user interactive elevated logon task for this executable. Legacy Run entries and outdated paths are reported as requiring repair. Submit `general.repair_startup:true` alone through `applyNativeSettings` to register/update and verify the task before removing the legacy Run entry. Explicit `general.auto_run:false` clears both product-specific registrations. Merely opening settings or applying unrelated changes never edits startup registration.

Source layout: `Native/TrafficMonitor/` (copied C++ project), `Native/OpenHardwareMonitorApi/`, `Native/include/`, `Media/` (C# WPF helper), `Lyrics.Core/` (copied independent core). Runtime packaging: `artifacts/builds/<timestamp>/TaskBarWidgets.exe`, adjacent `Media/` and `UI/` subdirectories, and native hardware DLLs next to the main executable. Source code never references original project paths outside TaskBarWidgets.

Display-item field keys use stable IDs: `items.native_0.order` / `items.builtin_FxOP34Lm.order`. The itemId descriptor is also emitted. Ordering persists in `item_order_ids`, retaining numeric `item_order` only for compatibility. UI submits the whole permutation and preserves draft edits made during an in-flight save.


## Native card channel

The quick cards are drawn inside `TaskBarWidgets.exe` on their own STA thread. Media is the server and the native card host is the client of a third current-user-only newline UTF-8 pipe: `TaskBarWidgets.Cards.<media PID>`. Both ends cap messages at4MiB. The protocol has exactly three messages:

- `cardSnapshot`: a complete, replaceable state. It carries the persisted `quickCards` configuration, media control state, audio endpoints, the structured `renderVersion:2` lyric frame with its style, the 84-day traffic display model, the weather status/current/details snapshot, update state, `statusText`, `connected` and `toolWindowTheme`. Every part carries its own revision, so a newer lyric frame can never evict the audio state. The first connection and every reconnection receive the full state.
- `cardRequest`: `{version:1,type:"command",action:"cardRequest",requestId,payload:{action,...}}`.
- `cardReply`: `{version:1,type:"command",action:"cardReply",requestId,success,payload|error}`; mutations answer with actual readback.

Requests and replies use a bounded reliable queue; only snapshots coalesce, so a pending image is never dropped. Every request is tagged with the connection generation captured at admission, and a reply for a retired connection is discarded. Card requests are limited to the actions the widgets need: `getState`, `getAudio`, `selectDevice`, `setVolume`, `setMute`, `mediaCommand`, `getTrafficHistory`, `weatherCommand`, `getUpdateState`, `downloadUpdate`, `cancelUpdateDownload`, `installUpdate` (requires `confirmed:true`), `openSettings`, `subscribeCardLyrics` and `cardSnapshot`. They execute through the same implementation the settings window uses, so device-switch, volume and mute ordering stays shared. `getTrafficHistory`, `weatherCommand` and `cardSnapshot` are answered from the same native snapshot Media already owns; the card host never scans files or waits on the network.

Device and source menus are drawn by a native popup window on the card thread (`Native/Cards/CardPopup.cpp`), anchored to the owning card, deciding its own monitor and DPI, and belonging to the group's effective area: a click inside it never dismisses the cards, and Escape closes the menu before the group. The same window answers `WM_GETOBJECT` with a native UI Automation provider (`Native/Cards/CardAccessibility.cpp`): each interactive entry of the interaction table becomes one element, buttons expose Invoke, sliders expose RangeValue, device/source selectors expose ExpandCollapse and heatmap cells expose SelectionItem. Because the table already drives painting, hit testing and keyboard navigation, the automation tree cannot drift from the painted one.

Media pushes `quickCards` (order, columns, enabled map, resource mode, font and `mica`) to the native host as a command whenever the settings are saved or reloaded, so the card group never re-derives configuration. Draft appearance from the settings window travels the other way: UI request `previewCardMica`/`previewCardTheme` → media pipe command `cardMicaPreview`/`cardThemePreview` → native preview state. A preview changes only what the card thread draws; committed values are replaced solely after a successful save and readback, and `hideCards` closes the group when settings opens.

## WinUI frontend channel

The settings process is started on demand — opening settings or confirming an update — and exits when its last window closes; nothing else keeps it resident. Media launches sibling `UI/TaskBarWidgets.UI.exe --host-pid <media PID> --pipe-name TaskBarWidgets.UI.<media PID>`. It owns a second current-user-only newline UTF-8 pipe; WinUI is the client. Both ends cap messages at4MiB. Requests use `{version:1,type:"command",action,requestId,payload}` and responses `{version:1,type:"command",action:"uiResult",requestId,success,payload,error}`. UI events are `openSettings` with optional page and `shutdown`. Foreground permission is delegated from native to media and then to UI for explicit user interaction. The UI watches its host PID. The post-update health handshake still starts the settings UI in update-health mode and exits it after the handshake; the updater already tolerates `uiPid=0`.

Actions: getState (media snapshot including source choices and local data-URL cover), getAudio (outputs/inputs, volumes0..1), mediaCommand, selectDevice, setVolume, setMute, getTrafficHistory, getNativeSettings/applyNativeSettings, getMediaSettings/applyMediaSettings, getFonts and settingsCommand. getFonts returns installed font choices as `[{value,label}]`; the native font-name length limit still applies. Media settings retain existing names/validation and provider/hotkey/lyric rules; advanced service commands return `{settings,events:[{type,payload}]}`. No old settings window is shown.

The `quickCards` object carries the persisted ordinary-card order, enabled map, resource mode, font, and `mica:{vivid,tintOpacity,luminosityOpacity,darkTintOpacity,darkLuminosityOpacity}` preference. All four opacity values are normalized to `tintOpacity:0..1` and `luminosityOpacity:0..1`; the user-facing transparency slider is `1 - luminosityOpacity`. `vivid` selects the tuned material; when it is `false` (or missing from an older payload) the cards use the plain system `MicaBackdrop` and the four values are kept for when it is switched back on. First install uses light `tint 0.10 / luminosity 0.85` (density 10%, transparency 15%) and dark `tint 0.15 / luminosity 0.90` (density 15%, transparency 10%); a neutral tint much above that washes the wallpaper out of the material. Individual missing or non-finite fields use those per-theme defaults. A payload containing only `tintOpacity,luminosityOpacity` is treated as legacy: it keeps the light values and derives dark values as `tint-0.02` and `luminosity-0.02`, matching the previous implicit dark-theme offset. The media settings keys `CardMicaVivid`, `CardMicaTintOpacity`, `CardMicaLuminosityOpacity`, `CardMicaDarkTintOpacity` and `CardMicaDarkLuminosityOpacity` round-trip through `settingsCommand` as `cardMicaVivid`, `cardMicaTintOpacity`, `cardMicaLuminosityOpacity`, `cardMicaDarkTintOpacity` and `cardMicaDarkLuminosityOpacity`. Settings files without `CardMicaVivid` predate the vivid material: their four values are reset once to the vivid defaults in memory (values tuned against the old, almost opaque wash) and written only by the next normal save; files that already carry the switch keep the user's own values, with explicit dark fields still winning over the legacy offset. The UI caches these values and applies both the material and the switch before opening. The four ordinary-card IDs are stable: `weather`, `traffic`, `device`, `media`; unknown/duplicate IDs are discarded and missing IDs appended during normalization. The update card is not an ordinary-card ID and never appears in this object. A disabled ordinary card stays in the settings list but is not constructed, laid out, refreshed, subscribed to lyrics, or included in outside-click hit testing; on-demand mode additionally destroys hidden card windows and their surfaces after ten minutes. The weather card always uses the fixed Apple-style layout and has no user-selectable module map.

For track offsets, the settings UI sends `trackOffsetsPageActivated` once for each explicit entry to the page and sends `queryTrackOffsets` for that entry, search, refresh and paging. Each query carries a monotonically increasing `requestId`; at most one query runs with one latest-wins trailing refresh, and a whole response is discarded when the page generation, current page or request ID has changed. Only the final valid batch is rendered.

Native module fields additionally expose `items.<stableId>.row` (0 or1). A changed module layout submits show/order/row for every module; horizontal_arrange switches one/two lanes without requiring different IDs. `item_rows` persists explicit lanes; numeric ordering remains only a migration compatibility field.

The UI bridge admits requests into two bounded FIFO lanes (16 waiting entries each): audio (`getAudio`, `selectDevice`, `setVolume`, `setMute`) and other requests. The card channel dispatches its own requests into the same handlers. Reading the pipe does not await request execution. Audio operations and replies retain their order; shutdown cancels queued work. A full lane returns a correlated error instead of allocating unbounded jobs.

Audio operations return `{outputs,inputs,operationSucceeded,message}` directly. Endpoint entries retain existing fields and add optional `canControl` (default true for older snapshots); false means volume/mute could not be read, so selectors remain usable but volume/mute controls are disabled. Partial default-role changes return actual readback with `operationSucceeded:false`. Mute changes only the mute property. UI request sequence and mutation generation prevent stale polls/replies from replacing new state; a stale snapshot must never drag a volume or progress slider back. Focus changes alone never dismiss cards.

## Weather settings and weather card

UI `weatherCommand` is forwarded to the native command of the same name, using existing request IDs/expiry. Native replies as `weatherResult`. Payload `operation` is `status`, `search`, `configure`, `refresh` or `result`. Provider 0 is China Weather; 1 is QWeather. Search takes `{provider,query}` and returns provider-specific `{id,name,region}` candidates. City selection is explicit; merely typing a display name cannot silently change the committed city ID.

`status` additionally returns a bounded structured `details` snapshot for the weather card and a monotonic `revision`/`stale` flag. `details` has `current` (`temperature`, `feelsLike`, `weather`, `conditionKind`, `humidity`, `windDirection`, `windScale`, `windSpeed`, `observedAt`), `forecast` (at most three normalized days), `airQuality`, and `alerts` (at most 16 entries). `conditionKind` is a provider-neutral icon/weather class derived in native code; UI must not parse raw provider icon codes. Missing or unsupported values remain empty and their module is hidden. Stored weather keys and raw provider responses never appear in the snapshot. A failed refresh retains the last successful details and marks `stale=true`; the snapshot city and `lastSuccessCity` remain separately identified.

Search/configure/refresh return `{jobId,pending,success,error,cities,status}`; UI polls `result` with a numeric job ID. Networking is serialized on the weather worker, while status/results return immediately on the native UI thread. Queue and retained job results are bounded. Late or cancelled search results cannot replace the current provider/search.

`configure` with `{provider,city:{id,name,region}}` saves and refreshes. `{credentialsOnly:true,apiHost,apiKey?,clearApiKey}` saves the QWeather connection without changing the current city/provider. Blank/omitted keys preserve the stored key; clearing requires the explicit flag. Keys travel only in that current-user local request and are never returned or logged. The existing local WeatherPro INI remains the storage location and must never be included in releases. QWeather credentials are sent only via HTTPS `X-QW-Api-Key` to a validated dedicated `*.qweatherapi.com` host, with redirects disabled.

Status includes selected provider/city, normalized API host, `hasApiKey`, update state, safe message, temperature, and attempt/success times. It never contains raw provider responses or secret values. Failures must remain visible; successful snapshots survive transient failures for the same location. Generic weather display preferences trigger a queued reload/refresh after saving rather than requiring an app restart.
