# 应用更新协议

固定源：`NoctisWang528/TaskBarWidget` 的 GitHub 正式 Release。版本为台北构建时间 `yymmdd-hhmm`，更新作业协议版本 2，架构 `win-x64`。下载不执行包内代码；仅用户确认后运行安装器。默认自动检查并下载，安装仍需确认。设置键 `ProductAutomaticUpdatesEnabled`，独立于停用的上游 `AutoCheckUpdates`。

本协议已接入产品；完整桌面更新链路的验收状态见 [ACCEPTANCE.md](../ACCEPTANCE.md)。旧版本缺少协调器或独立更新器时，必须先手动下载并迁移到完整新包。安装保持原目录，不更改启动登记或安装共享运行库。

## 分发格式

- Release 附件 `update.json`：`protocolVersion`, `version`, `architecture`, `assetName`, `size`, `sha256`, `fileManifestSha256`, `requirements`（`dotnetDesktop`, `windowsAppRuntime`, `windowsBuild`）。旧客户端固定更新 ZIP 名 `TaskBarWidgets-<version>-win-x64.zip`，它现在是兼容桥接包。手动安装使用独立的 `TaskBarWidgets-<version>-win-x64-portable.zip`（真实产品根目录布局），对应校验元数据为 `portable-update.json`。两者均列入 `SHA256SUMS.txt`。所有哈希为 SHA256 十六进制。
- ZIP 保持一个同名顶层目录；其中 `app-files.json`：`protocolVersion`, `version`, `architecture`, `files: [{path, bytes, sha256}]`。路径为安装根下正斜杠相对路径，清单不包含自身；更新器额外管理该清单。仅清单中的程序文件更新，不包含配置/数据/日志。
- ZIP 上限 512 MiB，展开上限 2 GiB，最多 8192 文件；拒绝重复/大小写冲突路径、绝对路径、越界、链接、设备名、ADS、尾随点/空格。程序文件只允许受管根文件以及 Media/UI/language/licenses 目录；根目录外设探针、兼容性 CSV/JSON、外设文档与 `Dependencies/HeadsetControl/{headsetcontrol.exe,HeadsetControl-4.1.0-source.zip,LICENSE,README.md}` 为精确程序文件例外。Dependencies 下其他文件、所有个人配置、数据库、缓存路径仍拒绝。旧客户端不认识这些新路径，不能直接接收 portable ZIP。

## UI / Media IPC

请求：`getUpdateState`, `checkForUpdates`, `downloadUpdate`, `cancelUpdateDownload`, `setAutomaticUpdates`（`enabled`）, `installUpdate`（`confirmed: true`）。长任务立即返回快照。`reportUiReady` 在 UI 初始化并连接后台后报告健康就绪；普通启动也可安全调用。

事件 `updateStateChanged` 的 payload 与快照一致：`revision`, `phase`, `currentVersion`, `latestVersion`, `notes`, `releaseUrl`, `bytesDownloaded`, `totalBytes`, `automaticEnabled`, `lastCheckedAt`, `error`, `message`, `canDownload`, `canInstall`。

phase：idle/checking/available/downloading/verifying/ready/preparing/installing/error/manualRequired。UI 在连接建立及 `uiReady` 后重新请求快照，只接受递增 revision；进度只更新现有控件，不重建设置页或覆盖草稿。自动更新选项默认开启、立即保存，与页面“应用更改”独立。

仅 `ready` 且 `canInstall` 时，在普通卡片组右侧显示一张约 220 DIP 宽、同主题的更新提示卡；主列按“快捷卡片”的自定义顺序排列，第二列只在更新就绪时出现，并与主列底部对齐。更新卡不参与普通卡片的启停、排序、索引或资源模式，只负责版本、状态、进度和“更新并重启”按钮；点击按钮进入与关于页相同的确认流程，重复点击不能创建并行确认／安装请求。下载完成不自动打开卡片、不发系统通知。安装前检查普通草稿、天气待保存城市／连接配置及天气保存刷新操作；存在未完成项时打开设置并说明原因，不自动保存或放弃。确认前后都核对候选仍可安装。

后台协调器位于 Media/Updates，类型 `UpdateCoordinator`：构造参数 installationRoot, currentVersion, automaticEnabled, onChanged（Action<UpdateSnapshot>），可选 cacheRootOverride、HttpMessageHandler 和 TimeProvider 供隔离测试；提供 Start、Initialization、Snapshot、Check(bool userInitiated=true)、Download、CancelDownload、SetAutomatic(bool)、PrepareInstall、SetInstallStatus(phase,error)、DisposeAsync。

启动先恢复缓存，自动检查延迟约 60 秒开始；以每日周期、已保存的检查时刻和下次检查／限流时间安排检查，不能以重启绕过 GitHub 退避。正式 Release 信息及附件仅允许固定仓库路径和受限 GitHub 下载域名的 HTTPS 重定向。下载有大小与时间界限，取消不触发安装；ZIP 与逐文件清单都需完整验证，恢复缓存及安装准备时再次校验。

`PreparedUpdate` 提供 Version、StageRoot、PackagePath、PackageSha256、FileManifestSha256、Requirements、CacheRoot。安装启动由宿主集成层负责，不在下载器里启动任何程序。

## 本地调试包推送（默认关闭）

### 新会话快速定位

“本地更新／传包／推包／更新器预留接口”都指本节的现有入口，无需发布 GitHub Release。仓库根目录与产品目录相差一层，先确认工作目录：

| 用途 | 从仓库根目录定位 |
| --- | --- |
| 推送已打好的本地包 | `TaskBarWidgets/scripts/push-local-update.ps1` |
| 制作可导入的附件目录 | `TaskBarWidgets/scripts/package-release.ps1` |
| 完整构建 | `TaskBarWidgets/scripts/build.ps1 -Configuration Release -Component All` |
| 管道协议和响应格式 | [IPC.md → Local update debug channel](../IPC.md#local-update-debug-channel) |
| 后台接口实现 | `TaskBarWidgets/Media/Updates/UpdateDebugServer.cs`、`UpdateCoordinator.cs` |

本地更新应优先走此接口。历史 `artifacts/` 下的临时替换脚本只是当时特定交付的记录，不是常规更新入口；不要复制旧脚本中的安装路径、版本和备份目录来执行新更新。

本地开发可把 `scripts/package-release.ps1` 生成的完整附件目录推送到**已经运行**的指定安装；目录必须同时包含 `update.json`、`SHA256SUMS.txt` 和对应桥接 ZIP；`update.json` 始终选择兼容外层包，不能改为 portable ZIP。构建、打包及任何调试产物放在本产品 `artifacts/` 下，不能把个人配置或天气密钥放进包。旧安装没有此接口时，需要先手动升级一次到包含此接口的完整版本；脚本不会启动、停止或替换产品，也不会修改注册表或开机启动。

### 准备本地包

从**仓库根目录**执行下面的构建／打包命令；已有与本轮源码一致、检查通过的完整构建时直接指定其目录，无需重复构建。`latest-build.txt` 只记录最近成功构建，多会话并行时要明确使用本轮构建目录。先完成该改动要求的检查，再打包。

```powershell
.\TaskBarWidgets\scripts\build.ps1 -Configuration Release -Component All

$buildDirectory = (Get-Content '.\TaskBarWidgets\artifacts\latest-build.txt' -Raw).Trim()
$buildInfo = Get-Content (Join-Path $buildDirectory 'build-info.json') -Raw | ConvertFrom-Json
$releaseDirectory = Join-Path (Resolve-Path '.\TaskBarWidgets').Path ("artifacts\candidates\local-update-" + $buildInfo.version)
.\TaskBarWidgets\scripts\package-release.ps1 -OutputDirectory $buildDirectory -ReleaseDirectory $releaseDirectory -AllowDirtyLocal
```

确认构建和打包各自成功后再进入下一步；失败时不要沿用旧的 `latest-build.txt` 或半成品附件目录。打包目标必须是 `artifacts/` 内的新目录，已经存在时另选候选目录，不覆盖旧交付。`-AllowDirtyLocal` 允许尚未提交的本地候选并记录来源状态，不代表可以公开发布。

从**仓库根目录**推送上述包：

```powershell
# 此路径是 Documents 下安装的常用候选；必须核实它就是正在运行的安装。
# 其他安装位置请替换变量，不要把源码目录或构建目录当作安装目录。
$installationDirectory = Join-Path $env:USERPROFILE 'Documents\TaskBarWidgets'
.\TaskBarWidgets\scripts\push-local-update.ps1 -InstallationDirectory $installationDirectory -ReleaseDirectory $releaseDirectory -EnableDebug
```

`-ReleaseDirectory` 传包含附件的目录，不是 ZIP 文件、ZIP 解压后的单一产品目录或原始 build 目录。实际导入选择 `update.json` 指定的不带 `-portable` 的 ZIP；不要把 `portable-update.json` 改名成 `update.json`。

### 推送、安装与关闭入口

在产品目录执行（示例路径请替换为实际安装与本地产物目录）；产品以管理员权限运行时使用同等权限的 PowerShell，脚本不自动提权：

```powershell
# 首次明确开启，并推送；以后省略 -EnableDebug 即可再次推送。
.\scripts\push-local-update.ps1 -InstallationDirectory 'C:\Apps\TaskBarWidgets' -ReleaseDirectory '.\artifacts\local-release' -EnableDebug
.\scripts\push-local-update.ps1 -InstallationDirectory 'C:\Apps\TaskBarWidgets' -ReleaseDirectory '.\artifacts\local-release'
# 单独关闭入口，不需要发布目录，也不要求产品正在运行。
.\scripts\push-local-update.ps1 -InstallationDirectory 'C:\Apps\TaskBarWidgets' -DisableDebug
```

开启标记为 `<安装目录>\Data\config\update-debug.enabled`，只以文件存在为开关；标记不得为 reparse point。Media 始终提供专用当前用户管道，但每次导入动态检查标记，默认拒绝。脚本只接受本地固定磁盘路径，拒绝路径链中的链接／junction，并在改变标记前检查安全性；`-EnableDebug` 与推送配合，`-DisableDebug` 为独立参数集，仅移除标记后返回。开启后即使本次导入失败，标记仍保留，需显式关闭。

脚本按完整映像路径查找唯一的运行中 `TaskBarWidgets.exe`，使用其 **Native PID**（不是 Media PID）连接 `TaskBarWidgets.UpdateDebug.<native PID>`。连接和写入各限 10 秒，完整导入响应限 5 分钟；超时或断线不代表导入已取消，请先查看现有更新 UI。请求／响应协议与边界见 [IPC.md](../IPC.md)。脚本不打印完整快照或配置。

本地包允许同版本和旧版本，以便重复调试；除此之外不放宽正常更新的元数据、架构、ZIP 大小与 SHA-256、`SHA256SUMS.txt`、清单哈希、逐文件大小／哈希、路径及包内文件集合检查。成功响应只在完整验证后返回，快照必须为 `ready`。之后仍由用户在现有关于页或更新卡确认安装，不能自动安装。

脚本没有 `-Install`、`-Force` 或无人值守安装参数。看到 `Local update verified and ready` 后，进入“设置 → 关于”的“更新并重启”，或从更新卡进入同一确认流程。不要为了安装而点击“检查更新”，那会切回正式发布通道。安装使用既有更新器完成正常退出、备份、清单替换及重启；确认最终 `journal.json` 为 `phase: complete`（桥接流程还需 `bridge: true`），并核对安装目录 `build-info.json` 的目标版本，才能报告“更新完成”。仅导入成功时应报告“已暂存，待应用内确认安装”。

本地候选只在当前会话有效，重启不恢复；本地候选暂存期间暂停自动检查，显式“检查更新”返回固定仓库的正式通道。关闭调试标记阻止后续导入及尚未开始的本地包安装，不会移除已经暂存的候选；需要重新开启或显式检查正式更新。安装确认、草稿保护、运行库预检、备份与恢复继续使用普通更新流程。

### 常见问题

| 现象 | 处理 |
| --- | --- |
| 找不到唯一运行中的安装 | 核对 `-InstallationDirectory` 与 Native EXE 的完整路径。使用 Native PID，不能使用 Media PID；不要为推包擅自启动或结束其他安装。 |
| 管道拒绝访问 | 日用程序已提权时，在同一用户的管理员 PowerShell 中运行脚本；不要放宽管道 ACL 或冒充受信任 UI 进程。 |
| 连接超过10秒或导入超过5分钟 | 检查该安装的 Media 是否运行、现有更新页面是否已有结果。超时不证明导入取消，不要立即重复推送。确属不支持接口的旧版本才安排一次手动升级。 |
| 导入成功但版本未改变 | `ready` 只是校验完成，继续应用内安装确认；检查未保存设置、正在保存的草稿和运行库提示。确认前保持调试标记存在。 |
| 元数据、清单或路径校验失败 | 检查附件是否来自同一次打包，是否误用 portable 包；修复包后重新打包，不通过改哈希、删清单或清空个人配置绕过。 |
| 安装中断或显示 `recoveryRequired` | 保留作业、journal 和备份，按下文[中断与恢复](#中断与恢复)处理；不要手写 `job.json`、强杀进程或覆盖活动安装。 |

## 跨版本根目录布局桥接

### 已发布客户端的硬限制

261109-2209、261110-1631 的实际 Media 程序集都会拒绝根目录 `TaskBarWidgets.PeripheralProbe.exe`、外设文档及 Dependencies 路径。原生更新器也校验传入清单与原安装清单，且确认后启动的是**安装中原有的更新器**，不是下载包内的新更新器。它们的 `ValidateMetadata` 还将附件名固定为 `TaskBarWidgets-<version>-win-x64.zip`。扩展新版白名单、改元数据附件名、只发布一个过渡版本，都不能解决跳过版本的用户。

兼容目标是已有协议 2 更新作业、协调器与原生更新器的安装，包括上述两个正式版本。实际发布 Media DLL 的 `InstallAsync.MoveNext` 均在 IL 648 加载协议常量 2，随后构造含唯一 `dataRoot` 的作业；这与附件 `update.json` 的元数据协议 1 不同。缺少更新器或仍使用协议 1 作业的安装需要先手动升级；桥接不会猜测旧个人数据根目录或放宽作业路径检查。

### 分发及正常交接

- portable ZIP 是完整的最终产品：外设 EXE、文档仍在安装根目录，HeadsetControl 在根目录 Dependencies 下。用户手动解压该 ZIP 后运行真实产品入口，不需要桥接。portable ZIP 不用于旧版应用内更新。
- 标准名更新 ZIP 是兼容外层包。已有合法程序文件沿用原路径，保留旧更新器运行库预检需要的 Media/UI runtimeconfig 和 WinUI bootstrapper。新的根目录文件、Dependencies 文件和真实主入口以 SHA256 前 16 个十六进制字符命名的 `.bin`（逐文件仍比较完整 SHA256，短名冲突会拒绝打包）放在 `Media/UpgradePayload/`，附最终 `manifest.json` 和绑定其哈希、版本的 `bridge.json`。外层 `TaskBarWidgets.exe` 是同包新版 `TaskBarWidgets.Updater.exe` 的相同字节副本；它只负责交接，不加载产品/媒体/UI。
- 旧 Media 按原协议完成完整外层 ZIP、清单与逐文件验证；既有用户确认、草稿保护、关闭审批和正常退出保持原流程。下载阶段不执行桥接代码。本地包推送也走同一外层协议，无需修改推送脚本或 IPC。
- 旧原生更新器按旧白名单备份并安装外层包，再以既有 `--update-health <job> <nonce>` 启动桥接入口。桥接核对原作业、安装位置、退出批准、nonce、仍在运行的旧 helper 映像与已记录的桥接 PID；仅接受本安装缓存中的协议 2 作业。
- 桥接对外层暂存目录重新做完整校验，并用新版**原有程序路径白名单**解析内层清单；每个最终文件必须匹配外层同路径文件或清单内哈希命名 blob 的大小与哈希。最终暂存目录再次校验准确文件集合、路径、大小、哈希和运行库。任何个人目录、越界、链接、未知 Dependencies 文件仍拒绝。新版 Media 在下载、缓存恢复和安装准备时也检查内层绑定；旧版不能理解内层，故由桥接在第一阶段健康应答前检查。
- 桥接写入 `bridge-pending.json` 和已列入外层清单的恢复指针，并预先生成新版 `BridgeRecovery.exe` 与 `recover.cmd`。第一阶段健康应答只表示桥接已验证并可接管，**不表示最终产品健康**。等待旧 helper 正常退出后，替换缓存作业中的 helper，启动 `--continue-bridge <原job> <桥接PID>`；桥接正常退出，后续 helper 核对进程身份并等待退出。
- 第二阶段继续使用同一个 job.json、nonce、journal 和原始备份，不创建指向中间版本的第二份备份。只为最终新增的受管程序路径扩展备份；个人数据及原文件不重新取快照。journal 增加可选 `bridge: true`（旧记录缺省 false），仍使用原事务阶段。安装最终清单后清除桥接健康信号，再启动真实产品要求 Native + UI 健康；此时的 `bridge: true` + `phase: complete` 才是最终完成。
- 最终 Apply 根据清单移除桥接 blob、恢复指针等运输文件，保留真实根目录布局。第二阶段失败或中断时，新 recover 会使用同一份**桥接前**备份恢复原程序和个人数据，而不是退回一个半安装桥接包；占用或不安全状态继续保留 journal 并要求恢复，不强杀进程。

为支持用户跳过任何中间版本，后续正式 Release 必须继续提供兼容外层包与 portable 完整包；不能只发一次桥接 Release 后恢复直接将新布局 ZIP 指向旧客户端。当前实现不另加网络下载、自动安装器、更新渠道或额外确认。内层目标与外层 Release 同版本，不能重定向到另一个 Release 或任意 URL。

### 中断与恢复

交接中断但尚未安装最终入口时，再运行安装目录中的桥接入口只恢复原先已经确认的作业，不建立新更新。`recover.cmd` 在旧 helper 完成前就已指向独立新版 `BridgeRecovery.exe`，因此不会被旧 helper 的“complete”状态误导为最终完成。原 job.json 继续绑定外层清单；最终清单的哈希经该外层 `bridge.json` 绑定，最终健康仍匹配原作业版本与 nonce。Native 健康入口校验安装／缓存位置、helper 身份与版本，不比较 `fileManifestSha256`；UI 就绪由 Media 转发，因此不要求原作业的外层哈希等于最终内层清单哈希。

显式 recover 在待续桥接阶段恢复原始版本；若 journal 已是 `bridge: true` / `complete` 或 `rolledBack`，则只报告终态。出现 `recoveryRequired` 时先正常关闭本安装，按原权限运行作业目录的恢复入口。保留该作业和备份；不要删清单、修改标记、替换个人数据，也不要通过清空配置来“修复”校验。

### 集成和验证命令

完整 build.ps1 已构建同一个 Updater.cpp；桥接代码由它包含 `Native/Updater/UpgradeBridge.h`，没有新项目或额外构建顺序。主构建流程无需新增桥接构建步骤。旧版 updater 二进制缺少 `TBW_BRIDGE_V1` 标记时打包脚本会拒绝，需先重新构建原生更新器。

```powershell
# 由主任务安排 .NET 构建槽；这里的测试不启动正常产品。
dotnet test .\tests\Media.Tests\TaskBarWidgets.Media.Tests.csproj --filter 'FullyQualifiedName~Updates'

# C++ isolated fixtures。传入实际旧版完整目录，只读取指定程序文件。
```

## 原生安装作业

独立静态 CRT Win32 程序 `TaskBarWidgets.Updater.exe` 随根入口分发，命令 `--job <job.json>` / `--recover <job.json>`。确认后将当前可信更新器复制到安装目录外的缓存 `%LOCALAPPDATA%/TaskBarWidgets/Updates/<安装路径哈希>/jobs/<guid>/` 运行，更新目标仍为原安装目录。作业 JSON 协议为 `protocolVersion: 2`，只传一个 `dataRoot`（省略旧的 `nativeDataRoot`、`mediaDataRoot`、`portableMode`），字段为 `protocolVersion`, `installRoot`, `stageRoot`, `workRoot`, `dataRoot`, `version`, `fileManifestSha256`, `requirements`, `nonce`, `nativePid`, `mediaPid`, `uiPid`。`dataRoot` 必须等于 `<installRoot>\Data`，并拒绝链接、越界路径和 AppData 路径。workRoot 等于 job.json 所在目录；backup、journal、status、health 均位于 workRoot，另生成 `recover.cmd` 供中断恢复。作业校验根路径、进程映像与受管文件路径；不接受任意删除目标。

更新器先检查清单/共享运行库/空间/权限，写 `status.json`（`phase: readyToExit` 或 `error`，含 `message`、`helperPid`）。Media 读到 readyToExit 才请求 Native `exitForUpdate`；Native 校验作业、nonce 及仍存活的准确 helper 映像，写入 `shutdown-approved.json` 后走正常保存退出。更新器必须同时见到匹配批准和上述旧进程正常退出（30 秒），不能仅因用户自行退出而替换程序。预检超时或交接失败写 `cancel.request` 取消尚未获准的作业，不强杀旧进程。

旧进程退出后再次校验暂存内容，备份实际程序及配置/数据库，再事务替换，入口 EXE 最后替换。仅按已知清单处理受管程序文件；不把整个目录当作可删除内容。替换后继续使用原安装位置及个人数据路径。

新主程序使用参数 `--update-health <job.json> <nonce>` 启动。Native 初始化完成并收到 Media 转发的 `updateUiReady` 后写 `health.json`（`nonce`, `version`, `ready: true`）。更新器等待 60 秒；失败先请求新主程序正常退出，关闭后回滚程序与数据，重新启动旧版。不安全的文件占用保留事务和备份并报告 recoveryRequired，绝不强行覆写活跃进程。

历史直接升级链路中，新版主程序的健康检查可读取 `protocolVersion: 1` 与 `2` 的作业，但更新器执行新作业时仍只写、只接受协议 2。协议 1 只用于验证安装根、作业目录、nonce、版本、更新器进程和状态，不用于推导新数据路径。此健康兼容本身不代表桥接包支持协议 1 作业；本节的桥接入口仍要求协议 2。升级完成后后续更新作业均为协议 2。

status 后续阶段包括 backingUp/installing/starting/complete/rolledBack/error/recoveryRequired。记录每一步的 journal 供 `--recover` 恢复；新版本健康后保留本次备份，再轮换更早的已完成备份。未完成作业不自动标为成功。正常入口发现本安装未完成的 journal 时阻止加载可能混合的程序，提示先运行作业目录的恢复入口；Media 可在下次启动说明上次失败。恢复前关闭该安装，使用同一用户及必要的原有管理员权限运行 `recover.cmd`，保留作业、日志和备份直到恢复完成。

Native `getUpdateContext` 返回 `installRoot` 和唯一 `dataRoot`；`exitForUpdate` 走正常保存退出；`updateUiReady` 报告 UI 初始化就绪。以上均沿用现有当前用户 IPC，不改变开机启动注册。

## 发布流程

正式发布仅在该次发布已经获得用户授权后执行，按以下顺序完成，避免客户端读取到附件尚未齐全的版本：

1. 提交准备发布的源代码，以构建开始时的 Asia/Taipei 时间生成 `yymmdd-hhmm` 版本；完整构建并运行包、运行库、UI 及更新器定向检查。不要把离屏或模拟宿主通过记录为真实更新重启验收。
2. 从干净构建运行 `scripts/package-release.ps1 -OutputDirectory <完整构建目录>`。产物为兼容更新 ZIP、真实布局的 portable ZIP、`SHA256SUMS.txt`、`update.json`、`portable-update.json`；各 ZIP 的单一同名根目录内有 `app-files.json`，不含个人配置、数据库、天气密钥、缓存、日志或探针图片，并保留许可证。打包脚本记录来源状态；`-AllowDirtyLocal` 只用于本地交付。打包完成前必须调用 `scripts/test-release-package.ps1`，通过已发布 Media 程序集中的真实 `ExtractAndVerify` 与 `VerifyStage` 完整验证 ZIP 和解压后的暂存目录；失败时不得发布。正式发行还应传入 `-CompatibilityDirectory <旧版完整目录>`（支持数组），在独立进程中用实际旧版校验器验证外层更新 ZIP。portable ZIP 只用新版校验器加 `-Portable` 验证，不能要求旧白名单接受它。
3. 在固定仓库创建对应版本的 **draft Release**，上传上述五个附件与发布说明；手动下载入口指向 portable ZIP，应用更新元数据仍指向固定名的兼容 ZIP。发布说明按“用户可见变更 → 升级注意事项 → 运行要求 → 附件与数据”组织；只写用户可见更新、操作方式、已知限制和兼容性，不写验证过程、测试结果、探针／构建／编译检查、桌面验收状态或内部检查细节，也不使用“验证”“测试”等开发过程标题。此时不要标为正式发布或预发布。
4. 从 draft 实际附件下载校验：文件名与版本一致；ZIP 的实际大小和 SHA-256 同时匹配 `update.json` 与 `SHA256SUMS.txt`；ZIP 内原始 `app-files.json` 字节的 SHA-256 匹配 `fileManifestSha256`；逐文件路径、大小及哈希完整且包内无清单外程序文件。附件检查针对上传后的内容，不能只核对本机产物。下载后对该目录再次运行 `scripts/test-release-package.ps1 -ReleaseDirectory <下载目录> -ValidatorDirectory <旧版完整构建目录>`；必要时把生成的 stage 交给 `scripts/test-updater.ps1 -PackageStage <stage>` 检查真实完整清单的原生安装预检，隔离夹具不批准退出，因此不会替换或启动包内产品。
5. 校验全部通过后才将 draft 发布为正式 Release。若有差异，保留为 draft 并重新制作／上传；不要让客户端把半成品当作最新版本。旧版正式 Release 没有协议附件时，客户端保持手动更新提示。

发布后若发现说明含验证或内部检查内容，应仅修订 Release 正文并复核全部 Release；除非用户另行说明，不改标题、标签、发布状态、Latest 标记或附件。

共享运行库仍由用户从微软官方下载并安装；更新器只校验要求，不自动下载或安装 .NET 或 Windows App Runtime，也不修改用户／系统环境变量。

## 程序资源路径兼容性

旧版更新器会拒绝 Settings、Data 等个人目录，只为既有的少数静态资源保留精确例外。新增程序资源应使用兼容路径（例如 `UI/Resources/SettingsNavigationResources.xbf`），不能先放入受保护目录、再仅在新版放宽白名单：旧版会在安装新版前拒绝整个包。保留原有 `UI/Settings/SettingsThemeResources.xbf` 例外，其他 Settings 文件继续拒绝。新建的 XAML 资源需同步更新引用，并验证最终 ZIP 不残留迁移前的 XBF。
