## 优先验证的假设

**H1（最强）原生请求队列在窗口重建后停摆。**
证据：一次成功 apply 之后，原生侧所有请求不再有日志，直到重启。候选机制：
  a. 唤醒消息投递给了即将销毁的窗口而丢失；`uiWakePosted` 停在 true，新窗口不再收到唤醒（`2af3b20` 针对这条，未验证）
  b. 原生 UI 线程真的卡住（`TaskBarDlg.cpp:92` 绘制路径里的 `MessageBox`、`RecreateAll` 设备重建、`SendSettingsToPlugin` 里的插件回调都可能无限期阻塞）
  c. 管道读线程退出/卡住（此时连"请求入队"都不会发生）
区分方法：在 `PostWake`、`ProcessIncoming` 入口、管道读循环各加一行带自增计数与 HWND 的日志，复现后看是"没有入队"还是"入队但没 Tick"。

**H2 色块来源未定位。**
虽然某帧实测 alpha=0，但用户看到实色块。需要确认色块来自监测绘图面（`ShowInfo`）还是媒体合成面（`m_media_presented=true` 时监测面被跳过，`TaskBarDlg.cpp:67`、`:526`）。取证：复现时截图 + 记录 `m_media_presented`、`IsTaskbarTransparent()`、`backgroundOpacity`、媒体是否在播放。

**H3 客户端取消语义。**
23.5s 的 `TaskCanceledException` 是 UI 主动取消，用户看到的"卡在保存中"可能只是没有反馈。需要看 UI 侧在等待时是否阻止重复提交、超时提示是否可见。
