# 2026-10-22 资源占用优化方案

本文件是 `Optimization` 分支的实施依据。基线提交 `1bdac39`（main，2026-10-22 11:07）已包含 `95d12f3` 的任务栏合成重建修复与透明度持久化修复。

## 1. 范围

- 保留三进程结构（`TaskBarWidgets.exe` / `TaskBarWidgets.Media.exe` / `TaskBarWidgets.UI.exe`）、无 WebView2、原生 Direct2D／DirectWrite／DirectComposition 媒体渲染与原生管道。
- 保留常用功能、低响应延迟、状态恢复能力、更新器与发布流程。
- 目标方向：常驻态的 Working Set、Private Working Set、Commit、分配率与 CPU。不设固定内存硬指标，以同一实例的相对改善与斜率判定。
- 不含：操作系统共享运行时大小、驱动与第三方叠加层、发行包体积、产品发布。

不接受的代价：稳定性、恢复速度、视觉正确性、输入响应、Explorer 重建与多 DPI 正确性、更新器可靠性。

响应优先级（验收排序，详见 §8.1）：

1. **卡片首次打开**：点击到卡片可见可交互的 p95 是硬指标，久置超过 10 分钟后的首次打开同样适用，任何释放策略不得使其退化。
2. **任务栏歌词与封面**：允许因重建产生额外延迟（目标 ≤300 ms、异步执行、不阻塞卡片与输入），不设 p95 硬指标。
3. **设置页**：仅在打开时加载，关闭后允许整体卸载内容树。

## 2. 现状与测量口径

外部观测（非本分支复测，仅作起点）：工作集合计约 580 MB、私有工作集合计约 227 MB、提交约 394 MB、空闲 CPU 约 6.7% 单核（24 逻辑核）。Media 播放时存在内存锯齿，停止后整体下降但 CPU 无明显下降。

硬性口径规则：

1. 不同构建、不同播放状态、不同计数方式的数字不可直接比较；旧版“稳定空闲”数据（约 323 MB 工作集）不作为播放基线。
2. Working Set 含共享页。三进程 WS 相加不等于占用，DXGI／D3D 运行时、共享 .NET 框架页与 WinUI 框架页会被重复计入。归因使用 Private Working Set 与 Commit。
3. 判据使用同一进程实例的差值（Δ）与循环斜率，不使用绝对值阈值。
4. 托管堆回落只说明不是托管保留，不构成泄漏已修复的证明。
5. 功能测试通过、离屏图像、包校验都不构成性能或内存验收。

## 3. 阶段 0：测量协议（前置，先做）

### 3.1 外部指标（零代码）

三进程分别采集：Working Set、Private Working Set、Commit、线程数、句柄数、CPU 时间增量。建议以 `scripts/measure-footprint.ps1` 固定采样间隔（1 s，60 s 窗口）与输出格式，结果落在忽略目录。

### 3.3 状态矩阵

同一进程实例内依次采集：启动、无媒体、播放歌词、播放频谱、打开卡片、关闭卡片、打开设置、关闭设置、换曲、停止播放、隐藏十分钟。固定条件：同一构建、`QuickCardResourceMode` 固定、固定曲目与来源、空载机器。

### 3.4 现象判定

- GC 保留：强制回收后托管堆下降而私有 WS 不降。
- 缓存：有容量上限，换曲 20 次后无单调斜率。
- 泄漏：同状态循环 50 次后句柄／提交出现单调斜率。
- 窗口生命周期：跨实例比较无效；Explorer 与 DPI 变化会改变图层尺寸，必须在同一实例内对照。

### 3.5 阶段 0 实施结果（2026-10-22，基线构建 `artifacts/builds/20261022-120729`）

**外部采样脚本**：`scripts/measure-footprint.ps1`

- 默认参数 `-IntervalSeconds 1 -DurationSeconds 60`；`-Label` 标记状态，`-BuildDirectory` 默认取 `artifacts/latest-build.txt`，`-OutputDirectory` 默认 `artifacts/measurements`（必须位于 `artifacts/` 内）。
- 默认拒绝采样 exe 路径不在 `-BuildDirectory` 下的进程，避免误测日常安装；`-AllowAnyProcessPath` 仅用于跨构建对照，不作为基线。
- 每 tick 每进程采集 Working Set、Private Working Set、Commit、Paged Memory、线程数、句柄数、CPU 累计时间，tick 区间内为增量；输出首值/末值/Δ/最小/最大/均值与最小二乘斜率（每秒）。产物为 `<时间戳>-<label>.csv`（逐秒）、`.json`（汇总+内部指标）、`raw-metrics.log`（窗口内内建计数原文）。
- Private Working Set 经 PDH `\Process(*)\Working Set - Private` 与 `\Process(*)\ID Process` 按 PID 关联。`QueryWorkingSetEx` 在本机各变体（数组、`AllocHGlobal` 字节长度、`[In,Out]` 修饰）对 explorer 与自身进程均返回成功但缓冲区全 0，已弃用；该路径下每进程只有一次查询，跨会话可用。PDH 缺该 PID 实例时记 `-1` 并告警，汇总中剔除该指标。
- 帧格式固定 `PDH_FMT_LARGE`（`0x00000400`）；`0x200` 是 `PDH_FMT_DOUBLE`，按 long 读会得到无意义数值。
- 内部计数按采样窗口过滤后同样输出 Δ 与速率：Media 读 `<build>/Media/Logs/app_debug-*.log` 的 `[METRICS]` 行；Native 读 `%APPDATA%\TaskBarWidgets\native-metrics.log`；UI 读 `<build>/UI/ui-metrics.log`（按目标 UI PID 过滤）。`getStateMaxMs` 为累计最大值，不进入速率列。

口径说明：

- Native 计数行不写曲目、路径或媒体内容，只含缓存与定时器计数；与 `native-media.log` 分开，便于采样而不读取失败诊断。
- Media 的 `pipeBytes` 为 JSON payload 字节，不含每帧 1 字节 LF；`getStateTextBytes` 不含 `SelectedSourceId`；`getState` 分支为让 `iconDataUrl` 只取一次引入了 `.Select(...).ToArray()`（每次小数组分配，已计入 `allocBytes`）。
- `UiRequestDispatcher.cs:99` 在回复写失败时会补发一条 `lane="reply"` 的同名计时，`getStateCount` 在该失败路径会多计 1 次，尚未加过滤。
- 方案 §3.2 原写 Native 用 `NativeMediaRenderer::Diagnostic()` 的既有 5 s 去重输出；实际 `Diagnostic()` 只返回最后一次失败文本（`NativeMediaRenderer.h:71`），5 s 去重辅助是 `NativeMediaHost::Diagnostic(stage,bytes,result)`（`NativeMediaHost.cpp:214-221`）。因此计数另走 `native-metrics.log`，不改动失败诊断。
- 方案 §3.2 表格中的 UI「HWND 数」未加内建计数：UI 侧没有稳定的 HWND 计数点，句柄数已由外部采样覆盖。
- UI 的 400 ms 定时器只在可见期间运行（`CardGroup.cs:145-154`），隐藏状态靠 `Hide()` 补写一行，故「关闭卡片」「隐藏十分钟」状态的 UI 行数为 1。

结论（均为同一实例的 Δ，不作跨实例绝对值比较）：

- 待机盘子：启动态与无媒体态合计 147–148 MB，两侧无差别；Native 空闲 CPU 约 34–38 ms/s、Media 约 23–24 ms/s，与方案 §2 的 6.7% 单核同量级。
- **最高占用状态不是播放本身，而是"播放过并打开过设置之后回到待机"：合计 295 MB**，比启动态高 148 MB（2.0×）。其中设置页首次打开一次贡献 UI +75.3 MB PWS／+85.1 MB Commit／+626 句柄，关闭设置后不回落（#8/#10 仍 135.8–136.3 MB），与 §5 阶段 3 的静态判断一致（`SettingsWindow` 走 `AppWindow.Hide()`、`UI/App.xaml.cs:245` 的 `Closed` 不触发、视觉树常驻）。
- 歌词播放：Native +25.1 MB PWS、+40.9 MB Commit、CPU 33.7→55.9 ms/s，句柄 +580；停止播放后 Native 停在 84.7 MB，不回落到 58.4 MB 基线 → 文字排版／画刷／封面缓存在停止播放后没有回收路径。
- 频谱：Media `allocBytes` 从 0.40 升到 4.75 MB/s（11.9×），FFT 37.7 次/s，Media PWS 峰值 80.8 MB（歌词态峰值 68.5 MB）；采集启动瞬间（12:38:21–12:38:41）分配峰值 40–77 MB/s（每 5 s 300–390 MB），gen2 1→2。与 OPT-004 的逐帧临时分配判断一致。
- `getState`：卡片可见时 2.34 次/s，每次 88 KB 图标 + 5.3 KB 封面 + 56 B 文本 ≈ 93.6 KB，管道约 0.28 MB/s；Media 侧 `getState` 均值 0.10 ms、最大 0.80 ms，成本在字节量而非 CPU → OPT-002 的收益体现在总字节与管道压力，不在服务端耗时。
- Native 图层：播放前 `layers=0/swapChains=0`，首次出现媒体内容时一次变 6/6，之后不再变；`textFormats` 24→47→29、`brushes` 32（触顶 `TrimBrushes` 上限）、`covers` 1→2、每张 `coverBytes=360000`（300×300×4）——封面实际按 300×300 解码，没有用到 2048 上限。
- UI 首开：`openMs=18.2 / firstFrameMs=135.0`（首次）、`9.3 / 80.1`（第二次），无超时；`imageCache=1`、`coverLoaded=1`、`sourceIcons=1`，缓存条目数与来源数一致，未发现泄漏式增长。
- 句柄：歌词窗口 Native +580、设置页 UI +626；关闭设置后 UI 句柄仍 +27 不回退。

指标区分度（用于后续阶段判据）：

- 有区分度：Private Working Set Δ、Commit Δ、Media `allocBytes`/s、FFT 次数/s、`getState`/s 与图标字节、各进程 CPU ms/s、Native `layers`、`coverBytes`、句柄数（设置页开合）。
- 区分度弱：Working Set 总量（共享页干扰）、线程数、Paged Memory。
- 需看包络不看单点：Media 空闲 PWS 在 74–81 MB 之间 GC 锯齿（同一窗口内 6 次 >1 MB 回落），单窗口 Δ 会把 GC 上升段当成增长 → 后续以谷值是否抬升与峰谷包络为准。

未采集／未验证：

- 换曲：窗口内没有换曲特征（`fft` 在 12:41:21 后恒为 6394、`frames` 递减），按未采集记录，需单独一轮。

### 阶段 2：频谱分配（OPT-004）

- 目标：16 ms 路径的常驻分配趋近于零。

- 细节：缓冲按采样代次失效；设备变化、单双声道、静音、停止播放路径全部保持现有语义；不改变帧发布节拍。
- 不做：不引入对象池，不改采集线程模型，不为省分配改变锁粒度。
- 验收：分配率显著下降且 CPU 不升；设备切换、单声道、静音、停止播放、代次竞态用例全绿。
- 回退：保留旧实现于开关之后一个阶段。
- 依赖：阶段 0 的分配率基线。

#### 实施结果（2026-10-22，构建 `artifacts/builds/20261022-134854`）

- 每帧缓冲改为租借：`GetSpectrum` 用 `Interlocked.Exchange(ref _idleScratch, null) ?? new SpectrumScratch()` 取一组 scratch（[SystemAudioSpectrumService.cs:156-228](Media/SystemAudioSpectrumService.cs)），`finally` 归还；并发或重入调用者取新组，不与在飞的帧交叉。`SpectrumScratch`（`:756-802`）只在声道数或采样窗变化时重建，内含 samples／real／imaginary／powers／magnitudes／bars。
- 调参快照：整帧只在第一段 `lock (_sync)` 内捕获一次 `_tuningSettings` 引用（`:172`），FFT 与 `CalculateBars` 共用同一代设置；每次调用的 `Clone()` 消失，也不存在"两段锁读到不同代设置"的窗口（`ApplyTuning` 先 Clone 再整体替换引用）。
- Hann 窗按长度缓存为静态 `ConcurrentDictionary<int, double[]>`（`:28`、`:582-592`），同一长度只计算一次；原实现每帧对每个样本重算 `0.5 - 0.5 * cos(...)`。

### 阶段 3：UI 常驻资源边界（OPT-003）

- 目标：区分“常驻进程”与“常驻视觉资源”，在卡片首开不退化的前提下降低稳态占用。
- 优先级依据：§8.1 的响应优先级——卡片首开为硬指标，任务栏歌词与封面允许重建延迟。
- 范围：释放条件由模式改为资源类型；空闲释放定时器按需启动；设置页关闭释放内容树、保留窗口壳。
- 保留清单（隐藏时不释放）：卡片 HWND、窗口位置、布局快照、最后媒体状态、连接与订阅、当前曲目封面位图（阶段 1 之后单张仅百 KB 至 2 MB 量级，保留可避免首开封面闪空）、卡片视觉树。
- 释放清单（隐藏超过阈值即可释放）：非当前曲目封面缓存、来源图标位图、歌词排版与扫描资源、Media 文字排版缓存、Native 文本布局缓存、设置页内容树。
- 歌词路径放宽：重建延迟目标 ≤300 ms，且必须异步，不得阻塞卡片可见或输入响应。
- 不做：不销毁卡片 HWND；不释放卡片视觉树（除非闲置超过 30 分钟且实测首开 p95 不受影响）；不主动 GC；不引入“最近使用”预热策略（需先量化）。
- 验收：隐藏 11 分钟后非当前曲目图像与排版缓存下降；久置后首次打开卡片 p95 不高于基线；歌词重建 ≤300 ms 且不阻塞 UI；焦点与更新卡行为不变。
- 回退：释放开关回到现行为。
- 依赖：阶段 0 的 p50/p95 与阶段 1 的封面尺寸口径。

## 8. 决策与待定

### 8.1 已定：响应优先级（2026-10-22）

卡片必须极快；任务栏歌词允许因资源重建而变慢。据此：

- 硬指标：点击到卡片可见可交互的 p95，包含闲置 10 分钟以上的首次打开。
- 软指标：歌词、封面在隐藏期被释放后的重建，目标 ≤300 ms，异步执行，不阻塞卡片与输入。
- 设置页：仅在打开时加载，关闭后释放内容树。
- 结论：Resident 模式以“首次打开 p95”为第一目标；内存只要求不随使用时长单调增长。

### 8.2 待定

- Media 层是否也存在与 `95d12f3` 同类的合成重建缺陷，需日志确认后才能决定是否修 `NativeMediaRenderer` 的失败分类。
